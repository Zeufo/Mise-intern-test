# Restaurant Booking REST API

REST API сервис для онлайн-бронирования столиков в ресторане.  
Тестовое задание на позицию **Backend Trainee · Python / FastAPI** в компанию **MISE**.

---

## 🛠 Стек технологий

- **Язык:** Python 3.12+
- **Фреймворк:** FastAPI (роутинг, Pydantic v2 валидация)
- **ORM / База данных:** SQLAlchemy 2.0 (Async) + aiosqlite (SQLite)
- **Менеджер пакетов:** `uv`
- **Логирование:** Loguru
- **Тестирование:** pytest | httpx.AsyncClien

---

## 🚀 Запуск проекта

### 1. Локальный запуск (с использованием `uv`)

1. **Клонировать репозиторий:**
   ```bash
   git clone https://github.com/Zeufo/Mice-intern-test.git
   cd Mice-intern-test
   ```

2. **Установить зависимости:**
   ```bash
   uv sync
   ```
3. **создать env файл по примеру .env.example:**
   ```bash
   cp .env.example .env
   ```
   
4. **Запустить сервер:**
   ```bash
   uv run uvicorn app.main:app --reload
   ```
   Сервер будет доступен по адресу: http://127.0.0.1:8000

### 2. Запуск тестов

Для запуска набора асинхронных тестов эндпоинтов и сервисного слоя:

```bash
uv run pytest
```

### 3. Запуск через Docker (опционально)

```bash
docker compose up --build -d
```

## 📖 Документация API

После запуска приложения интерактивная документация доступна по адресам:

- **Swagger UI:** http://127.0.0.1:8000/docs
- **ReDoc:** http://127.0.0.1:8000/redoc

### Основные эндпоинты

| Метод | Эндпоинт | Описание |
|-------|----------|----------|
| `POST` | `/bookings` | Создание брони (валидация полей, проверка пересечения слотов, возврат 201) |
| `GET` | `/bookings` | Получение списка броней (поддерживает фильтрацию `?booking_date=YYYY-MM-DD`) |
| `GET` | `/bookings/{id}` | Получение информации о брони по ID (404, если не найдена) |
| `DELETE` | `/bookings/{id}` | Отмена брони (Soft delete: меняет статус на `cancelled`) |

## 💡 Принятые архитектурные решения

1. **Многослойная архитектура:** Проект разделён на независимые слои (`api` → `services` → `database/models`), что исключает дублирование кода, изолирует бизнес-логику от транспортного уровня HTTP и упрощает покрытие тестами.

2. **Асинхронность (Async SQLAlchemy + aiosqlite):** Выбран полностью асинхронный стек работы с базой данных для обеспечения высокой пропускной способности I/O.

3. **Строгая валидация (Pydantic v2):** Все бизнес-правила (формат телефонов РФ, шаг слотов бронирования в 1 час с 12:00 до 22:00, ограничение даты в диапазоне +90 дней) инкапсулированы в Pydantic field validators, что гарантирует отдачу стандартных ошибок 422 при некорректных данных.

4. **Soft Delete:** Отмена бронирования реализована через изменение статуса записи на `cancelled` без физического удаления из базы данных для сохранения истории аудита.

## 🔮 Что бы я доделал при наличии дополнительного времени

1. **Система столиков (Table Management):** Добавил бы привязку броней к конкретным номерам столов и их вместимости, а не просто ограничение по часовому слоту.

2. **Миграции Alembic:** Настроил бы версионирование схемы БД через Alembic (для текущего ТЗ используется автоматическая инициализация через `metadata`).

3. **Фоновые задачи и нотификации:** Добавил бы Celery / Redis Streams или FastAPI BackgroundTasks для отправки SMS/Email подтверждений и напоминаний гостям о предстоящей брони.

4. **Rate Limiting:** Добавил бы ограничение частоты запросов (slowapi) на эндпоинт создания брони для защиты от спама.

5. **Расширенные фильтры и пагинация:** Добавил бы пагинацию (`limit` / `offset`) и фильтрацию по статусу брони (`active` / `cancelled`)

6. **Защита от race condition:** Текущая проверка вместимости слота (`SUM(guests)`) не атомарна — при параллельных запросах возможна гонка.
